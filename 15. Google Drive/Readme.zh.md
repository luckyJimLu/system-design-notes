# 第 15 章：设计 Google Drive

## 简介
Google Drive 是一种基于云的文件存储和同步服务，允许用户从各种设备存储、访问和共享文件。本章讨论设计具有以下功能的可扩展系统：
- **文件上传与下载**
- **跨设备文件同步**
- **文件共享**
- **文件修订历史**
- **编辑、删除和共享通知**

---

## 第 1 步：了解问题

### 主要要求
#### 功能要求：
- 上传和下载文件。
- 跨多个设备同步文件。
- 维护文件修订。
- 启用具有权限的文件共享。
- 发送有关文件编辑、删除和共享的通知。

#### 非功能性要求：
- **可靠性：** 数据丢失是不可接受的。
- **快速同步速度：** 避免用户对延迟同步不耐烦。
- **带宽效率：**最大限度地减少不必要的数据使用。
- **可扩展性：** 处理 1000 万每日活跃用户 (DAU)。
- **高可用性：** 在服务器故障或网络问题期间无缝运行。

### 约束和假设
- 用户获得 **10 GB 可用空间**。
- 最大文件大小：**10 GB**。
- 平均文件上传大小：**500 KB**。
- 上传频率：**每个用户每天 2 个文件**。
- 所需的总存储空间：**500 PB**。

### 迁移到分布式系统

#### 改进：
1. **分片：** 基于 `user_id` 在服务器之间分割存储。
2. **Amazon S3：** 使用 S3 进行可扩展和冗余的文件存储以及跨区域复制。

    <img src="./images/replication.png" alt="Replication" width="600" />
     
3. **负载均衡器：** 在多个 Web 服务器之间分配流量。
4. **元数据数据库复制：** 通过数据库分片和复制确保可用性。


#### 同步冲突：
对于像 Google Drive 这样的大型存储系统，同步冲突时常发生。
当两个用户同时修改同一个文件或文件夹时，就会发生冲突。

<div style="margin-left:5rem">
<img src="./images/sync-conflicts.png" alt="Sync Conflicts" width="600" />
</div>

- 在示例中，用户 1 和用户 2 尝试同时更新同一文件，但用户 1 的文件首先由我们的系统处理。
- 用户 1 的更新操作成功，但是用户 2 遇到同步冲突。
- 系统会显示同一文件的两个副本：用户 2 的本地副本和服务器的最新版本。
- 用户 2 可以选择合并两个文件或用另一个版本覆盖一个版本。

### 改进设计
<div style="margin-left:5rem">
<img src="./images/high-level-design.png" alt="High Level Design" width="500" />
</div>

1. **用户交互：**：用户通过浏览器或移动应用程序访问应用程序。

2. **块服务器：**
   - 文件被分割成 **4 MB 块**（最大大小）并分配唯一的哈希值。
   - 块独立存储在云存储（例如 Amazon S3）中。
   - 文件重建涉及按特定顺序连接块。

3. **云存储：** 块存储在云存储中以实现可扩展性和冗余。

4. **冷存储：** 非活动文件被移至冷存储以降低成本。

5. **负载均衡器：** 在 API 服务器之间均匀分配请求，以确保高效运行。

6. **API 服务器：**
   - 处理用户身份验证、配置文件管理和文件元数据更新。
   - 管理所有非上传工作流程。

7. **元数据数据库和缓存：**
   - 存储用户、文件、块和版本的元数据。
   - 经常访问的元数据会被缓存以加快检索速度。

8. **通知服务：**
   - **发布者/订阅者系统**，通知客户端有关文件更改（添加、编辑、删除）的信息。
   - 确保客户可以获取最新更新。

9. **脱机备份队列：** 临时存储文件更改信息，供脱机客户端在重新联机时同步。

### 文件上传流程

1. **文件上传：**
   - 文件由块服务器分割成块、压缩和加密。
   - 块被上传到块服务器并存储在S3中。
2. **元数据上传：**
   - 客户端将元数据发送到 API 服务器。
   - 元数据存储在数据库中，状态为 `pending`。
3. **完成：**
   - S3 触发回调将文件状态更新为 `uploaded`。
   - 通知服务通知相关用户。

### 文件下载流程
当在其他地方添加或编辑文件时，会触发下载流程。客户可以通过两种方式了解：
- 如果客户端 A 在线，而另一个客户端更改了文件，则通知服务将通知客户端 A。
- 如果客户端 A 离线，而另一个客户端更改文件，则数据将保存到缓存中。当离线客户端再次上线时，它会拉取最新的更改。

一旦客户端知道文件被更改，它首先通过 API 服务器请求元数据，然后
下载块来构建文件。

1. **触发器：** 通知服务通知客户端文件更新。
2. **元数据获取：** 客户端通过 API 检索更新的元数据。
3. **区块下载：**客户端从区块服务器下载更新的区块并重建文件。

### 通知服务
1. **目的：** 让客户了解文件更改的最新情况。
2. **机制：** 实现异步通知的**长轮询**。
3. **示例：** 添加、编辑或删除文件时，通知将推送到所有相关客户端。


---

### 存储优化
1. **重复数据删除：** 使用基于哈希的比较删除帐户级别的重复块。
2. **版本控制策略：**
   - 限制保存的修订版本的数量。
   - 优先考虑经常编辑的文件的最新版本。
3. **冷存储：** 将很少访问的文件移至更便宜的存储解决方案（例如 Amazon S3 Glacier）。

---

### 故障处理
1. **负载均衡器故障：**辅助负载均衡器变为活动状态。
2. **阻止服务器故障：** 挂起的任务将重新分配给其他服务器。
3. **元数据数据库故障：**
   - 将从节点提升为主节点。
   - 将流量重定向到剩余副本。
4. **云存储故障：** 使用跨区域复制来获取不可用的文件。
5. **通知服务失败：** 客户端重新连接到备用服务器。
