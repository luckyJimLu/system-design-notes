# 第 2 章：粗略估计

## 简介
粗略估计是系统设计面试中的一项关键技能。它涉及进行快速、粗略的计算来评估系统容量或性能。谷歌高级研究员 Jeff Dean 表示，这些估计有助于通过思想实验和通用性能基准来评估设计是否满足要求。

本章涵盖关键概念、方法和示例，以提高可扩展性和估算的能力。

### 每个程序员都应该知道的延迟数字
延迟数字表示计算系统中各种操作所花费的时间。这些提供了对相对性能的见解：

| 操作 | 延迟 (2020) |
|--------------------------|----------------|
| L1 缓存访问 | 0.5纳秒 |
| L2 缓存访问 | 7纳秒 |
| 主内存访问 | 100纳秒 |
| SSD随机读取 | 150微秒 |
| 硬盘随机寻道 | 10毫秒 |
| 数据中心往返 | 500微秒 |
| 跨区域数据中心 | 150毫秒 |

**关键见解：**
- 内存快，磁盘慢。
- 尽可能避免磁盘寻道。
- 在通过互联网传输之前压缩数据以节省带宽。


---

### 可用号码
高可用性 (HA) 可确保最短的停机时间。可用性以 **9** 表示：
- **99%（两个九）：** 每年约 3.65 天的停机时间
- **99.9%（三个九）：**每年停机时间约为 8.8 小时
- **99.99%（四个九）：**每年停机时间约为 52 分钟
- **99.999%（五个九）：**每年停机时间约为 5.3 分钟
- **99.9999%（六个九）：** ~31.56 秒/年的停机时间


Amazon、Google 和 Microsoft 等云提供商的目标是 **99.9% 或更高**的 SLA（服务级别协议）。

## 第 2 部分：示例估计 - Twitter QPS 和存储要求

### 假设
- **3 亿月度活跃用户 (MAU)。**
- **50% 每日活跃用户 (DAU)。**
- **平均推文/用户/天：** 2.
- **10% 的推文包含媒体内容。**
- **数据保留：** 5 年。

### 估计
1. **每秒查询次数 (QPS)：**
   - 日活跃用户 = \( 300M x 50\% = 150M \)
   - 推文 QPS = \( 150M x 2 条推文 / 24 小时 / 3600 秒 = ~3500 )
   - 峰值 QPS = \( 2 x 3500 = ~7000 \)

2. **媒体存储：**
   - **推文大小组成部分：**
     - `tweet_id`：64字节
     - `text`：140字节
     - `media`：1 MB
   - **每日媒体存储：** \( 150M x 2 x 10\% x 1MB = 每天 30TB \)
   - **5 年存储：** \( 30TB x 365 x 5 = ~55PB \)

## 第 3 部分：有效估算的技巧

### 1. 舍入和近似
精度并不重要；专注于过程。使用整数简化复杂的计算。例如：
- \( 99987 / 9.1 \) 可以近似为 \( 100,000 / 10 = 10,000 \)。

### 2. 写下假设
清楚地记录假设以供将来参考。

### 3. 标签单位
通过标记单位来避免歧义（例如，`5 MB` 而不是 `5`）。

### 4. 常见的估算场景
- **QPS（每秒查询数）：** 测量流量强度。
- **峰值 QPS：** 考虑流量峰值。
- **存储要求：** 估计总数据需求。
- **缓存要求：** 评估缓存的内存要求。
- **服务器数量：** 根据工作负载计算硬件需求。
