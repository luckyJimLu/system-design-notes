# 第 10 章：设计通知系统

## 简介
**通知系统**对于现代应用程序至关重要，它提供及时的更新，例如产品通知、事件、优惠和警报。通知可以通过以下方式发送：
1. **推送通知**（移动或桌面），
2. **短信**，以及
3. **电子邮件**。

本章重点介绍设计一个能够每天发送数百万条通知的可扩展系统。

---

## 第 1 步：了解问题
### 要求
- **通知类型：** 推送通知、短信和电子邮件。
- **交付：** 软实时系统，延迟最小。
- **平台：** iOS、Android 和桌面。
- **触发器：** 通知可以由客户端应用程序触发或在服务器上安排。
- **规模：**
  - **推送通知：** 1000 万条/天，
  - **短信：** 100 万条/天，
  - **电子邮件：** 500 万封/天。
- **选择退出支持：** 用户可以禁用特定的通知类型。

---

## 第 2 步：高层设计

### 组件

1. **通知类型：**
   - **iOS 推送通知：** 使用 **Apple 推送通知服务 (APNS)**。
   - **Android 推送通知：** 使用 **Firebase 云消息传递 (FCM)**。
   - **短信：** Twilio 或 Nexmo 等第三方服务。
   - **电子邮件：** 商业电子邮件服务，例如 SendGrid 或 Mailchimp。

2. **联系信息收集：**
   <div style="margin-left:3rem">
      <img src="./images/contact-info-gathering.png" alt="Contact Info Gathering" width="500">
   </div>

   - 在应用安装或注册期间收集设备令牌、电话号码或电子邮件地址。
   - 将联系信息存储在数据库中：
     - **设备令牌表：** 用于推送通知。
     - **用户表：** 用于电子邮件和电话号码。


3. **通知发送流程：**

   <div style="margin-left:3rem">
      <img src="./images/high-level-design.png" alt="High Level Design" width="500">
   </div>

   - **触发服务：**
      - 生成事件以启动通知（例如账单提醒、发货更新）。
      - 服务可以是微服务、cron 作业或触发通知发送事件的分布式系统。
   - **通知服务器：**
      - 为服务提供 API 来发送通知。
      - 进行基本验证以验证电子邮件、电话号码。
      - 查询数据库或缓存以获取呈现通知所需的数据。
   - **第三方服务：** 向用户发送通知。

     

### 初始设计中的挑战
- **单点故障 (SPOF)：** 一台通知服务器可能会导致整个系统崩溃。
- **可扩展性问题：** 难以独立扩展数据库、缓存和处理组件。
- **性能瓶颈：**发送通知的资源需求较高。

### 改进的设计

   <div style="margin-left:3rem">
      <img src="./images/improved-design.png" alt="Improved Design" width="500">
   </div>

- 将数据库和缓存移出通知服务器。
- 引入具有多个通知服务器的**水平扩展**。
- 使用**消息队列**来解耦系统组件。
   -  当要发送大量通知时，消息队列充当缓冲区。
- 添加从消息队列中提取通知事件并将其发送到相应第三方服务的工作人员。

   

---

## 第 3 步：深入设计

### 可靠性
1. **防止数据丢失：**
   <div style="margin-left:3rem">
   <img src="./images/data-loss.png" alt="Data Loss" width="400">
   </div>

   - 将通知数据保留在数据库中并实现重试机制。
   - 包含通知日志数据库以实现数据持久性。


2. **重复数据删除：**
   - 检查事件 ID 以避免发送重复的通知。
   - 当通知事件首次到达时，通过检查事件 ID 来检查之前是否见过该事件。
如果之前看到则丢弃它，否则发出通知。


### 附加组件
   <div style="margin-left:3rem">
   <img src="./images/events-tracking.png" alt="Events Tracking" width="400">
   </div>

1. **通知模板：** 预格式化模板可实现一致且高效的通知。
2. **通知设置：**
   - 用户可以选择加入或退出特定渠道（推送、短信或电子邮件）。
   - 存储在专用的通知设置表中。
3. **速率限制：** 限制发送给用户的通知的频率。
4. **重试机制：** 如果第三方服务失败，则重试发送通知。
5. **监控队列：** 跟踪排队通知以动态扩展工作人员。
6. **事件跟踪：** 收集打开率、点击率和参与度等指标。


### 安全性
- 使用 **AppKey** 和 **AppSecret** 对推送通知的 API 进行身份验证和保护。

### 通知流程

   <div style="margin-left:3rem">
   <img src="./images/updated-design.png" alt="Updated Design" width="500">
   </div>

1. 触发服务调用API来发送通知。
2. 通知服务器验证请求并从缓存或数据库中获取元数据。
3. 通知事件被发送到消息队列。
4. 工作人员处理事件并与第三方服务交互。
5. 第三方服务向用户发送通知。


---

## 关键优化
1. **水平扩展：** 添加更多通知服务器以进行负载分配。
2. **消息队列：** 解耦处理以处理大量数据。
3. **缓存：** 通过缓存经常访问的数据来减少延迟。
4. **分布式爬网：** 在地理位置上优化消息传递以获得更好的性能。
