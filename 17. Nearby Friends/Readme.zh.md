# 第17章：附近的朋友

## 简介

本章重点介绍为应用程序设计一个可扩展的后端，使用户能够共享他们的位置并发现**附近**的朋友。

与邻近章节的主要区别在于，在此问题中，**位置不断变化**，而在该问题中，企业地址或多或少保持不变。

---

## 第 1 步：了解问题并确定设计范围

推动面试的一些问题：
 * C：地理位置有多近才算“附近”？
 * I：5英里，这个数字应该是可配置的
 * C：距离是按直线距离计算还是考虑朋友之间的河流等
 * 我：是的，这是一个合理的假设
 * C：该应用程序有多少用户？
 * I：10亿用户，其中10%使用附近好友功能
 * C：我们需要存储位置历史记录吗？
 * I：是的，它对于机器学习等很有价值
 * C：我们可以假设不活跃的朋友会在 10 分钟内从该功能中消失吗
 * 我：是的
 * C：我们需要担心 GDPR 等吗？
 * 我：不，为了简单起见

### **功能要求**

 * 用户应该能够在他们的移动应用程序上看到附近的朋友。每个朋友都有一个距离和时间戳，表明位置何时更新
 * 附近的朋友列表应该每隔几秒更新一次

### **非功能性需求**

- **低延迟**：在没有太多延迟的情况下接收位置更新非常重要
- **可靠性**：偶尔的数据点丢失是可以接受的，但系统应该普遍可用
- **最终一致性**：位置数据存储不需要强一致性。不同副本中接收位置数据的几秒延迟是可以接受的

### **信封背面**

确定潜在规模的一些估计：
 * 附近的朋友是半径5英里以内的朋友
 * 位置刷新间隔为30s。人类行走速度较慢，因此无需过于频繁地更新位置。
 * 平均每天有 1 亿用户使用该功能 \w 10% 并发用户，即 1000 万
 * 平均一个用户有400个好友，他们都使用附近好友功能
 * 应用程序每页显示 20 个附近的好友
 * **位置更新 QPS** = 10mil / 30 == 每秒约 334k 次更新

## 第 2 步：提出高级设计并获得认可

在探索 API 和数据模型设计之前，我们将研究我们将使用的通信协议，因为它不像传统的请求响应通信模型那么普遍。

### **高层设计**

在高层，我们希望在对等点之间建立有效的消息传递。这可以通过点对点协议来完成，但这对于连接不稳定且功耗限制严格的移动应用程序来说并不实用。

更实用的方法是使用共享后端作为向您想要联系的朋友的扇出机制：

<div style="margin-left:3rem">
    <img src="./images/fan-out-backend.png" alt="fan-out-backend" width="500" />
</div>

后端是做什么的？
 * 接收来自所有活跃用户的位置更新
 * 对于每个位置更新，找到应接收该更新的所有活跃用户并将其转发给他们
 * 如果好友之间的距离超出配置的阈值，则不转发位置数据

这听起来很简单，但挑战在于根据我们正在运营的规模设计系统。

我们将首先从更简单的设计开始，并深入讨论更高级的方法：

<div style="margin-left:3rem">
    <img src="./images/simple-high-level-design.png" alt="simple-high-level-design" width="500" />
</div>

- **负载均衡器**：在 REST API 服务器和双向 Web 套接字服务器之间分散流量
- **Rest API 服务器**：处理辅助任务，例如管理好友、更新个人资料等
- **Websocket 服务器**：有状态服务器，将位置更新请求转发到相应的客户端。它还管理在初始化时向移动客户端播种附近朋友的位置（稍后详细讨论）。
- **Redis位置缓存**：用于存储每个活跃用户的最新位置数据。缓存中的每个条目都有一个 TTL 设置。当 TTL 过期时，用户不再处于活动状态，并且他们的数据将从缓存中删除。
- **用户数据库**：存储用户和好友数据。关系数据库或 NoSQL 数据库都可以用于此目的。
- **位置历史数据库**：存储用户位置数据的历史记录，不一定直接在附近好友功能中使用，而是用于跟踪历史数据以进行分析
- **Redis pubsub**：用作轻量级消息总线，为每个用户通道启用不同的主题以进行位置更新。

</div>

在上面的示例中，Websocket 服务器为连接到它们的用户订阅通道，并在收到位置更新时将其转发给适当的用户。

### **定期位置更新**

以下是定期位置更新流程的工作原理：

<div style="margin-left:3rem">
    <img src="./images/periodic-location-update.png" alt="periodic-location-update" width="500" />
</div>

 * 移动客户端向负载均衡器发送位置更新
 * 负载均衡器将位置更新转发到该客户端的 websocket 服务器的持久连接
 * Websocket服务器将位置数据保存到位置历史数据库
 * 位置数据在位置缓存中更新。 Websocket 服务器还将位置数据保存在内存中，以便为该用户进行后续距离计算
 * Websocket服务器通过redis pub sub在用户的频道中发布位置数据
 * Redis pubsub 向该用户频道的所有订阅者广播位置更新，即负责该用户好友的服务器
 * 订阅的 Web 套接字服务器接收位置更新，计算更新应发送给哪些用户并发送

这是同一流程的更详细版本：

</div>

平均而言，由于用户平均有 400 个朋友且其中 10% 一次在线，因此需要转发 40 个位置更新。

### **API设计**

我们需要支持的 Websocket 例程：
 * 定期位置更新 - 用户将位置数据发送到 websocket 服务器
 * 客户端接收位置更新 - 服务器发送好友位置数据和时间戳
 * websocket客户端初始化 - 客户端发送用户位置，服务器返回附近朋友的位置数据
 * 订阅新朋友 - websocket 服务器发送朋友 ID，移动客户端应该进行跟踪，例如朋友第一次在线时
 * 取消订阅朋友 - websocket 服务器发送朋友 ID，移动客户端应该取消订阅，例如朋友离线

HTTP API - 用于辅助职责的传统请求/响应有效负载。

### **数据模型**

 * 位置缓存将存储 `user_id` 和 `lat,long,timestamp` 之间的映射。 Redis 是此缓存的绝佳选择，因为我们只关心当前位置，并且它支持我们的用例所需的 TTL 驱逐。
 * 位置历史表存储相同的数据，但在关系表中存储上述四列。 Cassandra 可用于此数据，因为它针对写入密集型负载进行了优化。

## 第 3 步：深入设计

让我们讨论一下如何扩展高层设计，使其能够按照我们的目标规模运行。

### **每个组件的扩展能力如何？**

- **API 服务器**：可以通过自动缩放组和复制服务器实例轻松缩放
- **Websocket 服务器**：我们可以轻松地扩展 ws 服务器，但我们需要确保在拆除服务器时正常关闭现有连接。例如，我们可以在负载均衡器中将服务器标记为“正在耗尽”，并在最终从服务器池中删除之前停止向其发送连接
- **客户端初始化**：当客户端第一次连接到服务器时，它会获取用户的好友，在 redis pubsub 上订阅他们的频道，从缓存中获取他们的位置，最后转发给客户端
- **用户数据库**：我们可以根据user_id对数据库进行分片。通过由专门团队管理的专用服务和 API 公开用户/好友数据也可能是有意义的
- **位置缓存**：我们可以通过旋转多个 Redis 节点来轻松地对缓存进行分片。此外，TTL 对我们一次可以占用的最大内存设置了限制。但我们仍然想处理大量的写入负载
- **Redis 发布/订阅服务器**：我们利用这样一个事实：如果通道已初始化但未使用，则不会消耗内存。因此，我们可以为所有使用附近好友功能的用户预先分配通道，以避免处理诸如用户上线时打开新通道以及通知活动 websocket 服务器等问题。

### **深入研究 Redis 发布/订阅组件的扩展**

我们将需要大约 200GB 的内存来维护所有的发布/订阅通道。这可以通过使用 2 个每个 100GB 的 Redis 服务器来实现。

鉴于我们需要每秒推送约 1400 万次位置更新，但假设单个服务器每秒可以处理约 100k 次推送，那么我们至少需要 140 个 Redis 服务器来处理该负载量。

因此，我们需要一个分布式 Redis 服务器集群来处理密集的 CPU 负载。

为了支持分布式 Redis 集群，我们需要利用服务发现组件（例如 Zookeeper 或 etcd）来跟踪哪些服务器处于活动状态。

我们需要在服务发现组件中编码的是以下数据：

Web 套接字服务器使用从 Zookeeper 获取的编码数据来确定特定通道所在的位置。为了提高效率，哈希环数据可以缓存在每个 websocket 服务器的内存中。

在扩展或缩小服务器集群方面，我们可以设置一个日常作业，根据历史流量数据按需扩展集群。我们还可以过度配置集群来处理负载峰值。

Redis 集群可以被视为有状态存储服务器，因为为通道维护了一些状态，并且需要与订阅者进行协调，以便它们切换到集群中新配置的节点。

我们必须注意扩展操作过程中的一些潜在问题：
 * 由于通道的移动，网络套接字服务器将会产生大量重新订阅请求
 * 在操作过程中客户端可能会错过一些位置更新，这对于这个问题来说是可以接受的，但我们仍然应该尽量减少这种情况的发生。考虑在一天中流量最低时进行此类操作。
 * 我们可以利用一致的哈希来最大程度地减少添加/删除服务器时移动的通道数量

### **添加/删除好友**

每当添加/删除好友时，负责受影响用户的 websocket 服务器需要订阅/取消订阅好友的频道。

由于“附近的朋友”功能是大型应用程序的一部分，因此我们可以假设每当发生任何事件时都可以在移动客户端注册回调，并且客户端将向 websocket 服务器发送消息以执行适当的操作。

### **有很多朋友的用户**

我们可以对一个人可以拥有的朋友总数设置一个上限，例如 Facebook 的好友上限为 5000 个。

处理“鲸鱼”用户的 websocket 服务器可能会有更高的负载，但只要我们有足够的 web socket 服务器，就应该没问题。

### **Redis 发布/订阅的替代方案**

使用 Redis 进行发布/订阅的另一种方法是利用 Erlang——一种针对分布式计算应用程序进行优化的通用编程语言。

有了它，我们可以生成数百万个相互通信的小型进程。我们可以在分布式 erlang 应用程序中处理 websocket 连接和 pub/sub 通道。

然而，使用 Erlang 的一个挑战是，它是一种小众编程语言，可能很难找到强大的 erlang 开发人员。

## 第四步：总结

我们成功设计了一个系统，支持附近好友的功能。

核心组件：
- **Web 套接字服务器**：客户端和服务器之间的实时通信
- **Redis**：位置数据快速读写+pub/sub通道

我们还探索了如何扩展 Restful api 服务器、websocket 服务器、数据层、redis pub/sub 服务器，并且还探索了使用 Redis Pub/Sub 的替代方案。我们还探索了“随机附近的人”功能。
