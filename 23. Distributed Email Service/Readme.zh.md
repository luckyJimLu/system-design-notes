# 第23章：分布式电子邮件服务

## 简介

我们将设计一个**分布式电子邮件服务**，类似于本章中的**Gmail**。

2020 年，**Gmail** 拥有 18 亿活跃用户，而**Outlook** 在全球拥有 4 亿用户。

---

## 第 1 步：了解问题并确定设计范围

- C：有多少用户使用该系统？
- 一：10亿用户
- C：我认为以下功能很重要 - 身份验证、发送/接收电子邮件、获取电子邮件、过滤电子邮件、搜索电子邮件、反垃圾邮件保护。
- 我：很好的清单。现在不用担心身份验证。
- C：用户如何连接电子邮件服务器？
- I：通常，电子邮件客户端通过 SMTP、POP、IMAP 连接，但我们将使用 HTTP 来解决此问题。
- C：电子邮件可以有附件吗？
- 我：是的

### **非功能性需求**

- **可靠性** - 我们不应该丢失数据
- **可用性** - 我们应该使用复制来防止单点故障。我们还应该容忍部分系统故障。
- **可扩展性** - 随着用户群的增长，我们的系统应该能够处理它们。
- **灵活性和可扩展性** - 系统应该灵活且易于通过新功能进行扩展。我们选择 HTTP 而不是 SMTP/其他邮件协议的原因之一。

### **粗略估计**

- **10 亿用户**
- 假设一个人每天发送 10 封电子邮件 -> **每秒 10 万封电子邮件**。
- 假设一个人每天收到 40 封电子邮件，每封电子邮件平均有 50kb 元数据 -> **每年 730pb 存储**。
- 假设 20% 的电子邮件有存储附件，平均大小为 500kb -> **每年 1,460pb**。

## 第 2 步：提出高级设计并获得认可

### **邮件知识101**

有多种协议用于发送和接收电子邮件：
- **SMTP** - 用于从一台服务器向另一台服务器发送电子邮件的标准协议。
- **POP** - 用于从远程邮件服务器接收电子邮件并将其下载到本地客户端的标准协议。检索后，电子邮件将从远程服务器中删除。
- **IMAP** - 与 POP 类似，它用于从远程服务器接收和下载电子邮件，但它将电子邮件保留在服务器端。
- **HTTPS** - 从技术上讲不是电子邮件协议，但它可用于基于 Web 的电子邮件客户端。

除了邮件协议之外，我们还需要为电子邮件服务器配置一些 DNS 记录 - MX 记录：

### **传统邮件服务器**

当连接到单个服务器的用户数量有限时，传统邮件服务器可以很好地工作。

- Alice 登录她的 Outlook 电子邮件并按“发送”。电子邮件发送到 Outlook 邮件服务器。通过 SMTP 进行通信。
- Outlook 服务器查询 DNS 以查找 gmail.com 的 MX 记录，并将电子邮件传输到其服务器。通过 SMTP 进行通信。
- Bob 通过 IMAP/POP 从他的 Gmail 服务器获取电子邮件。

在传统邮件服务器中，电子邮件存储在本地文件系统中。每封电子邮件都是一个单独的文件。

磁盘可能会损坏并且服务器可能会停机。

### **分布式邮件服务器**

分布式邮件服务器旨在支持现代用例并解决现代可扩展性问题。

这些服务器仍然可以支持用于本机电子邮件客户端的 IMAP/POP 和用于跨服务器邮件交换的 SMTP。

但对于基于 Web 的丰富邮件客户端，通常使用基于 HTTP 的 RESTful API。

API 示例：
- `POST /v1/messages` - 将邮件发送到“To”、“Cc”、“Bcc”标头中的收件人。
- `GET /v1/folders` - 返回电子邮件帐户的所有文件夹

响应示例：


```
[{id: string        Unique folder identifier.
  name: string      Name of the folder.
                    According to RFC6154 [9], the default folders can be one of
                    the following: All, Archive, Drafts, Flagged, Junk, Sent,
                    and Trash.
  user_id: string   Reference to the account owner
}]
```


- `GET /v1/folders/{:folder_id}/messages` - 返回文件夹下的所有消息 \w 分页
- `GET /v1/messages/{:message_id}` - 获取有关特定消息的所有信息

响应示例：


```
{
  user_id: string                      // Reference to the account owner.
  from: {name: string, email: string}  // <name, email> pair of the sender.
  to: [{name: string, email: string}]  // A list of <name, email> paris
  subject: string                      // Subject of an email
  body: string                         //  Message body
  is_read: boolean                     //  Indicate if a message is read or not.
}
```


这是分布式邮件服务器的高层设计：

<div style="margin-left:3rem">
    <img src="./images/high-level-architecture.png" alt="high-level-architecture" width="500" />
</div>

- **网络邮件** - 用户使用网络浏览器发送/接收电子邮件
- **Web 服务器** - 面向公众的请求/响应服务，用于管理登录、注册、用户配置文件等。
- **实时服务器** - 用于向客户端实时推送新的电子邮件更新。我们使用 websockets 进行实时通信，但对于不支持它们的旧浏览器，我们会回退到长轮询。
- **元数据数据库** - 存储电子邮件元数据，例如主题、正文、发件人、收件人等。
- **附件存储** - 对象存储（例如Amazon S3），适合存储大文件。
- **分布式缓存** - 我们可以在 Redis 中缓存最近的电子邮件以改善用户体验。
- **搜索存储** - 分布式文档存储，用于支持全文搜索。

电子邮件发送流程如下所示：

<div style="margin-left:3rem">
    <img src="./images/email-sending-flow.png" alt="email-sending-flow" width="500" />
</div>

- 用户写一封电子邮件并按“发送”。电子邮件被发送到负载均衡器。
- 负载均衡器速率限制过多的邮件发送和路由到其中一台 Web 服务器。
- 如果域与发件人相同，Web 服务器会执行基本的电子邮件验证（例如电子邮件大小）并短路出站流。但首先会检查垃圾邮件吗？
- 如果基本验证通过，电子邮件将发送到消息队列（附件从对象存储引用）
- 如果基本验证失败，电子邮件将发送到错误队列
- SMTP 传出工作人员从传出队列中提取邮件，进行垃圾邮件/病毒检查并路由到目标邮件服务器。
- 电子邮件存储在“已发送电子邮件”文件夹中

我们还需要监视传出消息队列的大小。增长太大可能表明存在问题：
- 收件人的邮件服务器不可用。我们可以稍后使用指数退避重试发送电子邮件。
- 没有足够的消费者来处理负载，我们可能必须扩展消费者。

<div style="margin-left:3rem">

- 传入电子邮件到达 SMTP 负载平衡器。邮件被分发到SMTP服务器，在那里完成邮件接受策略（例如无效的电子邮件被直接丢弃）。

### **元数据数据库**

以下是电子邮件元数据的一些特征：
- 标头通常很小且经常访问
- 正文大小从小到大不等，但通常会读取一次
- 大多数邮件操作都是隔离给单个用户的 - 例如获取电子邮件、标记为已读、搜索。
- 数据新近度影响数据使用。用户通常只阅读最近的电子邮件
- 数据具有高可靠性要求。数据丢失是不可接受的。

在 gmail/outlook 规模上，数据库通常是定制的，以减少每秒输入/输出操作 (IOPS)。

让我们考虑一下我们有哪些数据库选项：
- **关系数据库** - 我们可以为标题和正文构建索引，但这些数据库通常针对小数据块进行优化。
- **分布式对象存储** - 这可能是备份存储的一个不错的选择，但不能有效地支持搜索/标记为已读/等。
- **NoSQL** - Gmail 使用 Google BigTable，但它不是开源的。

根据以上分析，现有的解决方案似乎很少能完美满足我们的需求。
在面试环境中，设计新的分布式数据库解决方案是不可行的，但重要的是要提及以下特性：
- 单列可以是一位数 MB
- 数据一致性强
- 旨在减少磁盘 I/O
- 高可用和容错
- 应该很容易创建增量备份

为了对数据进行分区，我们可以使用`user_id`作为分区键，从而将一个用户的数据存储在单个分片上。
这禁止我们与多个用户共享电子邮件，但这不是本次采访的要求。

让我们定义表：
- 主键由分区键（数据分布）和聚簇键（数据排序）组成
- 我们需要支持的查询 - 获取用户的所有文件夹，显示文件夹的所有电子邮件，创建/获取/删除电子邮件，获取已读/未读电子邮件，获取对话线程（奖励）

### **电子邮件送达率**

设置服务器来发送电子邮件很容易，但由于垃圾邮件防护算法的原因，将电子邮件发送到收件人的收件箱却很困难。

如果我们只是设置一个新的邮件服务器并开始通过它发送邮件，我们的电子邮件可能最终会进入垃圾邮件文件夹。

我们可以采取以下措施来防止这种情况发生：
- **专用IP** - 使用专用IP发送电子邮件，否则收件人服务器将不会信任您。
- **对电子邮件进行分类** - 避免从同一服务器发送营销电子邮件，以防止更重要的电子邮件被分类为垃圾邮件
- **慢慢预热您的 IP 地址**，在大型电子邮件提供商中建立良好的声誉。新IP需要2到6周的预热时间
- **快速禁止垃圾邮件发送者**，以免损害您的声誉
- **反馈处理** - 与 ISP 建立反馈循环，以跟踪投诉率并快速禁止垃圾邮件帐户。
- **电子邮件身份验证** - 使用常见技术来打击网络钓鱼，例如发件人策略框架、域名密钥识别邮件等。

你不需要记住所有这些。只要知道构建一个好的邮件服务器需要大量的领域知识。

### **搜索**

搜索包括基于电子邮件内容进行全文搜索或基于发件人、收件人、主题、未读等过滤器进行更高级的查询。

电子邮件搜索的一个特点是它是用户本地的，并且写入多于读取，因为我们需要在每次操作时重新索引它，但用户很少使用搜索选项卡。

让我们比较一下谷歌搜索和电子邮件搜索：

|               | 适用范围 | 排序 | 准确度 |
|---------------|----------------------|---------------------------------------|---------------------------------------------------|
| 谷歌搜索 | 整个互联网 | 按相关性排序 | 索引需要一些时间，所以不是立竿见影的结果。 |
| 电子邮件搜索 | 用户自己的邮箱 | 按属性排序，例如时间、日期等 | 索引应该快速并且结果准确。 |

要实现此搜索功能，一种选择是使用 Elasticsearch 集群。我们可以使用`user_id`作为分区键将同一节点下的数据分组：

突变操作通过 Kafka 异步进行，以便将服务与重新索引流程分离。
实际上，搜索数据是同步发生的。

Elasticsearch 是最流行的搜索引擎数据库之一，并且很好地支持电子邮件的全文搜索。

或者，我们可以尝试开发自己的自定义搜索解决方案来满足我们的特定要求。

设计这样的系统超出了范围。构建它时的核心挑战之一是针对写入密集型工作负载进行优化。

为了实现这一点，我们可以使用日志结构合并树（LSM）来构建磁盘上的索引数据。写入路径仅针对顺序写入进行了优化。
该技术用于 Cassandra、BigTable 和 RocksDB。

其核心思想是将数据存储在内存中，直到达到预定义的阈值，然后将其合并到下一层（磁盘）中：

<div style="margin-left:3rem">
    <img src="./images/lsm-tree.png" alt="lsm-tree" width="500" />
</div>

两种方法之间的主要权衡：
- Elasticsearch 可在一定程度上进行扩展，而自定义搜索引擎可以针对电子邮件用例进行微调，从而使其能够进一步扩展。
- Elasticsearch 是我们需要与元数据存储一起维护的一项单独服务。自定义解决方案可以是数据存储本身。
- Elasticsearch 是一个现成的解决方案，而自定义搜索引擎则需要大量的工程工作来构建。

## 第四步：总结

其他谈话要点：
- **容错** - 系统的许多部分都可能发生故障。我们如何处理节点故障是值得的。
- **合规性** - 鉴于欧洲的 GDPR 法律，PII 需要以合理的方式存储。
- **安全** - 电子邮件加密、网络钓鱼防护、安全浏览等。
- **优化** - 例如，防止不同用户多次发送相同附件的重复。
