# 第 1 章：从零扩展到数百万用户

## 简介
扩展系统以支持数百万用户是一个复杂的迭代过程，需要细化和优化。本章概述了如何从单个服务器设置开始，并逐步扩展架构以处理数百万用户。

---

## 第 1 部分：单服务器设置
最初，所有组件（Web 应用程序、数据库、缓存）都在单个服务器上运行。

<div style="margin-left:3rem">
   <img src="./images/single-server.png" width="400" />
</div>

### 请求流程
1. 用户通过域名（例如 `api.mysite.com`）访问应用程序，使用 DNS 解析为 IP 地址。
2. Web 服务器的 IP 地址返回到浏览器或移动应用程序。
3. HTTP 请求发送到 Web 服务器，Web 服务器返回 HTML 或 JSON 响应。

### 流量来源
1. **Web 应用程序：** 使用服务器端语言（例如 Python、Java）进行业务逻辑，使用客户端语言（例如 JavaScript、HTML）进行演示。
2. **移动应用程序：** 使用 HTTP 和 JSON 与 Web 服务器进行通信，以进行轻量级数据交换。

---

## 第 2 节：数据库分离
随着用户群的增长，数据库被移动到专用服务器，以允许独立扩展 Web 层和数据库层。

<div style="margin-left:3rem">
   <img src="./images/database.png" width="400" />
</div>

### 数据库选择

1. **关系数据库 (SQL)：** 存储在表中的结构化数据。示例：MySQL、PostgreSQL。
2. **非关系数据库（NoSQL）：**适合非结构化数据或低延迟要求。类别包括：
   - 键值存储
   - 图数据库
   - 列存储
   - 文件存储

- 在以下情况下，非关系数据库可能是正确的选择：
   - 应用程序需要超低延迟。
   - 数据是非结构化的，或者没有关系数据。
   - 只需要序列化和反序列化数据（JSON、XML、YAML 等）。
   - 需要存储大量数据。

---

## 第 3 节：垂直缩放与水平缩放
### 垂直缩放
- 向现有服务器添加更多资源（CPU、RAM）。
- 受硬件限制，缺乏冗余。

### 水平缩放
- 向池中添加更多服务器，使其更适合大型系统。
- 负载均衡器用于处理服务器之间的请求路由。
---

## 第 4 部分：负载均衡器

<div style="margin-left:3rem">
   <img src="./images/load-balancer.png" width="400" />
</div>

**负载均衡器**在多个服务器之间分配流量。好处包括：
1. 冗余：如果服务器离线，流量将重新路由。
   -  如果服务器 1 离线，所有流量将路由到服务器 2。
2. 可扩展性：轻松添加服务器以应对流量高峰。
   -  如果网站流量快速增长，可以添加后续服务器来处理额外的流量。

---

## 第 5 节：数据库复制

<div style="margin-left:3rem">
   <img src="./images/database-replication.png" width="400" />
</div>

### 主从模型
- **主数据库：** 处理写入操作。
   - 所有数据修改命令（例如插入、删除或更新）都必须发送到主数据库。
- **从属数据库：** 处理读取操作，提高性能和可靠性。
   - 由于在大多数应用程序中读取与写入的比率较高；因此，奴隶的数量
系统中的数据库数量通常大于主数据库的数量。

### 好处
1. 通过并行读取操作提高性能。
2. 通过冗余实现高可用性和数据可靠性。


### 故障处理
- 如果只有一个从库可用，并且离线，则读取操作将被定向
临时到主数据库。
- 当有多个从库时，读操作
重定向到其他健康的从数据库，新服务器将取代旧服务器。
-  如果主数据库离线，从数据库将被提升为新数据库
大师。
- 在生产系统中，所选的从数据库可能不是最新的，因此需要通过运行数据来更新数据
恢复脚本（多主机和循环复制等方法可能会有所帮助）。

## 第 6 节：缓存
**缓存**将频繁访问的数据存储在内存中以减少数据库负载。缓存层是一个临时数据存储层，比数据库快得多。

<div style="margin-left:3rem">
   <img src="./images/cache.png" width="500" />
</div>

### 缓存注意事项
1. **用例**：当数据频繁读取但不频繁修改时，请考虑使用缓存。
2. **过期策略：** 一旦缓存数据过期，就会从缓存中删除。当没有过期策略时，缓存
数据将永久保存在内存中。
3. **一致性：**这意味着保持数据存储和缓存同步。不一致
之所以会发生这种情况，是因为数据存储和缓存上的数据修改操作不在单个事务中。
4. **缓解故障**：单个缓存服务器代表潜在的单点故障、多个
建议跨不同数据中心的缓存服务器以避免单点故障 (SPOF)。
5. **逐出策略：**：一旦缓存已满，需要逐出项目以释放内存。 LRU 是最流行的缓存驱逐策略。

---

## 第 7 节：内容分发网络 (CDN)
**CDN** 通过在地理分布的服务器上缓存静态内容（图像、CSS、JavaScript）来缩短加载时间。

<div style="margin-left:3rem">
   <img src="./images/cdn.png" width="400" />
</div>

### 工作流程
1. 用户从最近的 CDN 服务器请求内容。
2. 如果不可用，将从源服务器获取内容并缓存。


### CDN注意事项
1. **成本：** CDN 由第三方提供商运营，他们对进出 CDN 的数据传输收取费用。
2. **缓存过期：**缓存过期时间既不能太长也不能太短。
3. **CDN 后备：** 如果出现临时 CDN 中断，客户端应该能够检测到问题
并向源头请求资源。
4. **使文件失效：**如果文件被更新，则缓存应该失效以指向更新的文件。

通过将会话数据移动到共享数据存储，Web 服务器变得无状态。这允许：
1. 更容易水平缩放。
2. 根据流量自动缩放。

## 第 9 节：多数据中心设置
跨多个数据中心部署可提高可用性并减少延迟。策略包括：

<div style="margin-left:3rem">
   <img src="./images/data-center.png" width="400" />
</div>

1. **GeoDNS 路由：** 将用户引导至最近的数据中心。
2. **数据复制：** 跨中心同步数据以防止不一致。

### 关键考虑因素
- **流量重定向：**需要有效的工具将流量引导到正确的数据中心。
- **数据同步：**常见的策略是跨多个数据中心复制数据。
- **测试和部署：** 自动化部署工具对于保持所有数据中心的服务一致至关重要。

## 第 10 节：消息队列
**消息队列**是一个持久组件，存储在内存中，支持异步
沟通。它充当缓冲区并分发异步请求。

<div style="margin-left:3rem">
   <img src="./images//message-queue.png" width="500" />
</div>

- 输入服务（称为生产者/发布者）创建消息并将其发布到消息队列。
- 其他称为消费者/订阅者的服务连接到队列，并执行消息定义的操作。

## 第 12 节：数据库扩展
### 垂直缩放
- 添加硬件资源，但存在物理和成本限制。
- 有多个缺点：
   -  单点故障的风险更大。
   -  垂直扩展总体成本较高

### 水平扩展（分片）

<div style="margin-left:3rem">
   <img src="./images/horizontal-scaling.png" width="400" />
</div>

- 使用键（例如 `user_id`）将数据划分到多个分片。
   - 分片将大型数据库分成更小、更容易管理的部分，称为分片。
   - 每个分片共享相同的架构，但每个分片上的实际数据对于该分片来说是唯一的。
-  实施分片策略时，分片键至关重要。选择分片键时，选择能够均匀分布数据的键非常重要。

#### 挑战
1. **重新分片数据：** 在以下情况下需要重新分片数据：
   - 由于快速增长，单个分片无法再容纳更多数据。
   - 由于数据分布不均匀，某些分片可能比其他分片更快地耗尽分片。
   - 一致性哈希就是用来克服这些问题的

2. **名人问题：** 对特定分片的过多访问可能会导致服务器过载。
   - 为了解决这个问题，我们可能需要为每个名人分配一个分片。

3. **连接和反规范化：** 一旦数据库被跨多个服务器分片，就很难跨数据库分片执行连接操作。
   -  常见的解决方法是对数据库进行非规范化，以便可以在单个表中执行查询。

---

## 结论
### 要点
1. 保持 Web 层无状态。
2. 在每一层建立冗余。
3. 使用缓存和 CDN 来优化性能。
4. 通过分片扩展数据层。
5. 解耦组件以获得灵活性。

本章为构建可处理数百万用户的可扩展系统提供了坚实的基础。
