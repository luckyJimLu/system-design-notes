# 第 11 章：设计新闻源系统

## 简介
**新闻源系统**显示来自用户连接的不断更新的帖子列表（状态更新、照片、视频和链接）。示例包括 Facebook 的新闻源、Instagram 的源和 Twitter 的时间线。本章探讨可扩展新闻源系统的设计。

---

## 第 1 步：了解问题

### 要求
1. **平台：** 该系统支持网络和移动应用程序。
2. **特点：**
   - 用户可以发布帖子。
   - 用户可以在新闻源中查看朋友的帖子。
3. **排序：** 为了简单起见，提要按 **逆时间顺序** 排序。
4. **规模：**
   - 用户最多可以有 5,000 个好友。
   - 1000 万每日活跃用户 (DAU)。
   - 提要可以包括文本、图像和视频。

---

## 第 2 步：高层设计

### 概述
该设计包括两个主要流程：
1. **提要发布：** 用户发布帖子，该帖子将写入数据库并传播到其朋友的提要。
2. **新闻提要构建：** 用户通过按时间倒序聚合朋友的帖子来检索他们的新闻提要。

---

### 新闻提要 API
1. **提要发布API：**
   - **端点：** `POST /v1/me/feed`
   - **参数：** `content`（发布文本）和`auth_token`（身份验证）。

2. **新闻提要检索 API：**
   - **端点：** `GET /v1/me/feed`
   - **参数：** `auth_token`（身份验证）。

---

### 提要发布

1. **用户交互：** 用户通过 feed 发布 API 发布帖子。
2. **负载均衡器：** 将流量分配到 Web 服务器。
3. **Web 服务器：** 验证请求并重定向到服务。
4. **帖子服务：** 将帖子存储在数据库和缓存中。
5. **扇出服务：** 将帖子传播到缓存中朋友的新闻源。
6. **通知服务：** 向朋友发送通知。

### 新闻提要大楼

1. **用户交互：** 用户通过检索 API 请求新闻源。
2. **负载均衡器：** 将流量分配到 Web 服务器。
3. **Web 服务器：** 将请求转发到新闻提要服务。
4. **新闻源服务：** 从新闻源缓存中获取帖子 ID，并从数据库或缓存中检索完整的帖子详细信息。

## 第 3 步：深入设计

### Feed 发布深入探讨
1. **网络服务器：**
   - 使用 `auth_token` 对用户进行身份验证。
   - 实施速率限制以防止垃圾邮件。

2. **扇出服务：**
   - **写入时的扇出：** 在写入时将帖子推送到朋友的提要。
     - **优点：** 实时更新，快速提要检索。
     - **缺点：** 对于有很多朋友的用户来说，资源密集。
   - **阅读时的扇出：** 在阅读时拉取帖子。
     - **优点：** 对于不活跃的用户来说非常有效。
     - **缺点：** 饲料检索速度较慢。
   - **混合方法：** 对大多数用户使用推送模型，对高连接用户（例如名人）使用拉动模型。

        <img src="./images/feed-publishing-deep-dive.png" alt="Feed Publishing Deep Dive" width="500">

**扇出服务**的工作原理如下：

    1. **获取好友 ID：** 从图形数据库中检索好友列表。
    2. **从缓存中过滤好友：** 访问缓存中的用户设置以排除某些好友（例如，静音的好友或选择性共享首选项）。
    3. **发送到消息队列：** 将过滤后的好友列表连同新的帖子 ID 一起发送到消息队列进行处理。
    4. **扇出工作人员：**工作人员从消息队列中检索数据并更新新闻提要缓存。缓存存储 `<post_id, user_id>` 映射而不是完整的用户和帖子对象以节省内存。
    5. **存储在新闻源缓存中：** 将新帖子 ID 附加到好友的新闻源缓存中。可配置的限制可确保仅存储最近的帖子，因为大多数用户都关注最新内容，从而使缓存内存消耗保持在可控范围内。

## 新闻提要检索深入研究

### 缓存架构
缓存分为五层：
1. **新闻源缓存：** 存储帖子 ID 以便快速检索。
2. **内容缓存：** 存储帖子详细信息（热缓存中的热门帖子）。
3. **社交图缓存：** 存储用户关系数据。
4. **操作缓存：** 跟踪用户操作（点赞、回复、分享）。
5. **计数器缓存：** 维护点赞、回复、关注者等的计数。

## 关键优化

### 缩放
1. **数据库扩展：**
   - 水平扩展和分片。
   - 使用只读副本进行高流量查询。
2. **无状态 Web 层：** 保持 Web 服务器无状态以启用水平扩展。

### 缓存
1. 将经常访问的数据存储在内存中。
2. 使用缓存层来减少延迟和数据库负载。

### 可靠性
1. **一致的哈希：** 在服务器之间均匀分配请求。
2. **消息队列：** 解耦系统组件并缓冲流量。

### 监控
1. 跟踪 QPS（每秒查询数）和延迟等关键指标。
2. 监控缓存命中率并相应调整配置。
