# 第21章：广告点击事件聚合

## 简介
**数字广告**是一个大产业，伴随着Facebook、YouTube、TikTok等的崛起。

因此，跟踪广告点击事件很重要。在本章中，我们将探讨如何设计 Facebook/Google 规模的**广告点击事件聚合**系统。

数字广告有一个称为**实时竞价 (RTB)** 的流程，在此过程中买卖数字广告库存：

<div style="margin-left:3rem">
    <img src="./images/digital-advertising-example.png" alt="digital-advertising-example" width="500" />
</div>

RTB 的速度很重要，因为它通常在一秒钟内发生。
数据准确性也非常重要，因为它会影响广告商支付的金额。

根据广告点击事件聚合，广告主可以做出调整目标受众和关键词等决策。

## 第 1 步：了解问题并确定设计范围
 - C：输入数据的格式是什么？
 - I：每天10亿次广告点击，总共200万个广告。广告点击事件数量同比增长 30%。
 - C：我们的系统需要支持哪些最重要的查询？
 - I：最需要考虑的查询：
   - 返回广告 X 在过去 Y 分钟内的点击事件数
   - 返回过去 1 分钟内点击次数最多的 100 个广告。这两个参数都应该是可配置的。每分钟都会发生聚合。
   - 上述查询支持按`ip`、`user_id`、`country`进行数据过滤
 - C：我们需要担心边缘情况吗？我能想到的一些：
   - 有些事件可能会晚于预期到达
   - 可能有重复的事件
   - 系统的不同部分可能会宕机，所以我们需要考虑系统恢复
 - I：这是一个很好的清单，考虑一下这些
 - C：延迟要求是多少？
 - I：广告点击聚合有几分钟的端到端延迟。对于 RTB，不到一秒。广告点击聚合存在延迟是可以接受的，因为这些延迟通常用于计费和报告。

### **功能要求**
 - 聚合最近Y分钟内`ad_id`的点击次数
 - 每分钟返回前 100 个点击次数最多的 `ad_id`
 - 支持不同属性的聚合过滤
 - 数据集量达到 Facebook 或 Google 规模

### **非功能性需求**
 - 聚合结果的正确性非常重要，因为它用于 RTB 和广告计费
 - 正确处理延迟或重复事件
 - 鲁棒性——系统应该能够适应部分故障
 - 延迟 - 最多几分钟的 e2e 延迟

### **粗略估计**
 - 10 亿日活跃用户
 - 假设用户每天点击 1 个广告 -> 每天 10 亿次广告点击
 - 广告点击 QPS = 10,000
 - 峰值 QPS 5 倍数 = 50,000
 - 一次广告点击占用0.1KB存储空间。每日存储需求为 100GB
 - 每月存储空间 = 3tb

## 第 2 步：提出高级设计并获得认可
在本节中，我们将讨论查询 API 设计、数据模型和高层设计。

### **查询API设计**
API是客户端和服务器之间的契约。在我们的例子中，客户是仪表板用户 - 数据科学家/分析师、广告商等。

这是我们的功能需求：
 - 聚合最近Y分钟内`ad_id`的点击次数
 - 返回最近 M 分钟内点击次数最多的前 N 个 `ad_id`
 - 支持不同属性的聚合过滤

我们需要两个端点来实现这些要求。可以通过其中之一的查询参数来完成过滤。

**最近M分钟内ad_id的总点击次数**：


```
GET /v1/ads/{:ad_id}/aggregated_count
```


查询参数：
 - 从 - 开始分钟。现在默认为 - 1 分钟
 - 到结束分钟。默认是现在
 - filter - 不同过滤策略的标识符。例如，001 表示“非美国点击”。

回应：
 - ad_id - 广告标识符
 - count - 开始和结束分钟之间的聚合计数

**返回最近 M 分钟内点击次数最多的前 N 个 ad_ids**


```
GET /v1/ads/popular_ads
```


查询参数：
 - 计数 - 点击次数最多的前 N 个广告
 - window - 聚合窗口大小（以分钟为单位）
 - filter - 不同过滤策略的标识符

回应：
 - ad_ids 列表

为了支持快速返回过去 M 分钟内点击次数最多的前 N 个广告，我们还将维护以下结构：
| 最多点击的广告 |           |                                                  |
|--------------------|-----------|--------------------------------------------------|
| 窗口大小 | 整数 | 聚合窗口大小（M）（以分钟为单位） |
| 更新时间分钟 | 时间戳 | 最后更新的时间戳（以 1 分钟为粒度） |
| 最多点击的广告 | 数组 | JSON 格式的广告 ID 列表。 |

存储原始数据和存储聚合数据之间有哪些优缺点？
 - 原始数据可以使用完整的数据集，并支持数据过滤和重新计算
 - 另一方面，聚合数据使我们能够拥有更小的数据集和更快的查询速度
 - 原始数据意味着拥有更大的数据存储和更慢的查询
 - 然而，聚合数据是派生数据，因此存在一些数据丢失。

在我们的设计中，我们将结合使用这两种方法：
 - 保留原始数据以供调试是个好主意。如果聚合出现bug，我们可以发现bug并回填。
 - 为了提高查询性能，还应该存储聚合数据。
 - 原始数据可以冷存储，以避免额外的存储成本。

当涉及到数据库时，有几个因素需要考虑：
 - 数据是什么样的？它是关系型、文档型还是 Blob 型？
 - 工作负载是读重、写重还是两者兼而有之？
 - 是否需要交易？
 - 查询是否依赖于 SUM 和 COUNT 等 OLAP 函数？

对于原始数据，我们可以看到平均QPS为10k，峰值QPS为50k，因此系统是写入密集型的。
另一方面，读取流量较低，因为原始数据主要用作出现问题时的备份。

关系数据库可以完成这项工作，但扩展写入可能具有挑战性。
或者，我们可以使用 Cassandra 或 InfluxDB，它们对繁重的写入负载有更好的本机支持。

另一种选择是将 Amazon S3 与 ORC、Parquet 或 AVRO 等列式数据格式结合使用。由于这个设置不熟悉，我们将坚持使用 Cassandra。

对于聚合数据，由于不断查询聚合数据以获取仪表板和警报，因此读写工作负载都很重。
它也是写入密集型的，因为聚合服务每分钟都会聚合和写入数据。
因此，我们也将在这里使用相同的数据存储 (Cassandra)。

### **流式处理与批处理**
我们提出的高层架构是一种流处理系统。
以下是三种类型系统之间的比较：
|                         | 服务（在线系统） | 批处理系统（离线系统） | 流媒体系统（近实时系统） |
|-------------------------|-------------------------------|--------------------------------------------------------|----------------------------------------------|
| 反应能力 | 快速回复客户 | 无需回复客户 | 无需回复客户 |
| 输入 | 用户请求 | 具有有限大小的有界输入。数据量大 | 输入没有边界（无限流） |
| 输出 | 对客户的回应 | 物化视图、聚合指标等。 | 物化视图、聚合指标等。 |
| 绩效衡量 | 可用性、延迟 | 吞吐量 | 吞吐量、延迟 |
| 示例 | 网上购物 | 映射减少 | 弗林克 [13] |

在我们的设计中，我们混合使用了批处理和流处理。

我们使用流式处理数据到达并近乎实时地生成聚合结果。
另一方面，我们使用批处理来备份历史数据。

一个系统同时包含两种处理路径——批处理和流处理，这种架构称为 lambda。
缺点是您有两个处理路径，需要维护两个不同的代码库。

Kappa 是一种替代架构，它将批处理和流处理结合在一个处理路径中。
关键思想是使用单个流处理引擎。

### **时间**
我们需要一个时间戳来执行聚合。它可以在两个地方生成：
 - 事件时间 - 广告点击发生时
 - 处理时间-服务器处理事件时的系统时间

Due to the usage of async processing (message queues) and network delays, there can be significant difference between event time and processing time.
 - 如果我们使用处理时间，聚合结果可能不准确
 - 如果我们使用事件时间，我们必须处理延迟事件

没有完美的解决方案，我们需要考虑权衡：
|                 | 优点 | 缺点 |
|-----------------|---------------------------------------|--------------------------------------------------------------------------------------|
| 活动时间 | 聚合结果更准确 | 客户端可能有错误的时间或时间戳可能是由恶意用户生成的 |
| 处理时间 | 服务器时间戳更可靠 | 如果事件迟到，则时间戳不准确 |

由于数据准确性很重要，因此我们将使用事件时间进行聚合。

### **交货保证**
由于我们聚合的数据将用于计费，因此数据准确性是首要任务。

因此，我们需要讨论：
 - 如何避免处理重复事件
 - 如何确保所有事件都得到处理

我们可以使用三种交付保证——最多一次、至少一次和恰好一次。

在大多数情况下，当少量重复项可以接受时，至少一次就足够了。
然而，我们的系统并非如此，因为微小百分比的差异可能会导致数百万美元的差异。
因此，我们需要使用一次性传递语义。

### **重复数据删除**
最常见的数据质量问题之一是重复数据。

它可以来自多种来源：
 - 客户端 - 客户端可能会多次重新发送同一事件。恶意发送的重复事件最好由风险引擎处理。
 - 服务器中断 - 聚合服务节点在聚合过程中发生故障，并且上游服务尚未收到确认，因此重新发送事件。

### **容错**
在聚合节点内，我们正在内存中处理数据。如果节点出现故障，处理的数据就会丢失。

一旦另一个节点填补空缺，我们就可以利用 kafka 中的消费者偏移量从我们离开的地方继续。
然而，我们需要维护额外的中间状态，因为我们要在 M 分钟内聚合前 N 个广告。

### **数据监控和正确性**
由于我们聚合的数据对于计费至关重要，因此进行严格的监控以确保正确性非常重要。

我们可能想要监控的一些指标：
 - **延迟**：可以跟踪不同事件的时间戳，以了解系统的端到端延迟
 - **消息队列大小**：如果队列大小突然增加，我们需要添加更多聚合节点。由于 Kafka 是通过分布式提交日志实现的，因此我们需要跟踪记录滞后指标。
 - **聚合节点上的系统资源**：CPU、磁盘、JVM等。

我们还需要实现一个协调流程，这是一个批处理作业，在一天结束时运行。
