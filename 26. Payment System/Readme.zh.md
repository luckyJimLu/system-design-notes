# 第26章：支付系统

## 简介
我们将在本章中设计一个**支付系统**，它支撑着所有现代**电子商务**。

**支付系统**用于结算金融交易，转移货币价值。

---

## 第 1 步：了解问题并确定设计范围
 * C：我们正在建设什么样的支付系统？
 * I：电子商务系统的支付后端，类似于 Amazon.com。它处理与资金流动相关的一切。
 * C：支持哪些付款方式——信用卡、PayPal、银行卡等？
 * I：系统应该支持现实生活中的所有这些选项。为了采访的目的，我们可以使用信用卡付款。
 * C：我们自己处理信用卡处理吗？
 * I：不，我们使用第三方提供商，如 Stripe、Braintree、Square 等。
 * C：我们的系统中是否存储信用卡数据？
 * I：出于合规原因，我们不会将信用卡数据直接存储在我们的系统中。我们依赖第三方支付处理器。
 * C：该应用程序是全局的吗？我们需要支持不同的货币和国际支付吗？
 * I：该申请是全球性的，但我们假设仅使用一种货币进行采访。
 * C：我们每天支持多少笔支付交易？
 * I：每天100万笔交易。
 * C：我们是否需要支持支付流程，例如每月向付款人支付？
 * 我：是的，我们需要支持
 * C：还有什么需要注意的吗？
 * I：我们需要支持协调，以解决与内部和外部系统沟通中的任何不一致之处。

### **功能要求**
 * 收款流程——支付系统代表商户从客户处收款
 * 付款流程 - 支付系统向世界各地的卖家汇款

### **非功能性需求**
 * 可靠性和容错性。付款失败需谨慎处理
 * 需要建立内部和外部系统之间的协调。

### **粗略估计**
系统每天需要处理100万笔交易，即每秒10笔交易。

对于任何数据库系统来说这都不是一个高吞吐量，因此这不是本次采访的重点。

### **付款流程**
以下是付款流程的高级概述：

<div style="margin-left:3rem">
    <img src="./images/payin-flow-high-level.png" alt="pay-in-flow-high-level" width="500" />
</div>

 * 支付服务 - 接受支付事件并协调支付流程。它通常还会使用第三方提供商对反洗钱违规或犯罪活动进行风险检查。
 * 付款执行者 - 通过付款服务提供商 (PSP) 执行单个付款订单。支付事件可能包含多个支付订单。
 * 支付服务提供商(PSP) - 将资金从一个帐户转移到另一个帐户，例如从买家的信用卡帐户转移到电子商务网站的银行帐户。
 * 卡计划 - 处理信用卡操作的组织，例如 Visa MasterCard 等。
 * 分类账 - 保存所有支付交易的财务记录。
 * 钱包 - 保存所有商家的账户余额。

以下是付款流程示例：
 * 用户点击“下订单”，支付事件将发送到支付服务
 * 支付服务将事件存储在其数据库中
 * 支付服务为所有支付订单调用支付执行器，这是支付事件的一部分
 * 支付执行器将支付订单存储在其数据库中
 * 支付执行器调用外部PSP处理信用卡支付
 * 支付执行者处理支付后，支付服务更新钱包以记录卖家有多少钱
 * 钱包服务将更新的余额信息存储在其数据库中
 * 支付服务调用分类账记录所有资金变动

### **支付服务API**

```
POST /v1/payments
{
  "buyer_info": {...},
  "checkout_id": "some_id",
  "credit_card_info": {...},
  "payment_orders": [{...}, {...}, {...}]
}
```


示例 `payment_order`：

```
{
  "seller_account": "SELLER_IBAN",
  "amount": "3.15",
  "currency": "USD",
  "payment_order_id": "globally_unique_payment_id"
}
```


注意事项：
 * `payment_order_id`被转发到PSP以消除重复支付，即它是幂等密钥。
 * 金额字段为 `string`，因为 `double` 不适合表示货币值。


```
GET /v1/payments/{:id}
```


该端点根据`payment_order_id`返回单笔支付的执行状态。

### **支付服务数据模型**
我们需要维护两个表 - `payment_events` 和 `payment_orders`。

对于支付来说，性能通常不是一个重要因素。然而，强一致性是。

选择数据库的其他考虑因素：
 * 雇用 DBA 来管理数据库的强大市场
 * 该数据库已被其他大型金融机构使用的良好记录
 * 配套工具丰富
 * 传统 SQL 优于 NoSQL/NewSQL 的 ACID 保证

以下是 `payment_events` 表包含的内容：
 * `checkout_id` - 字符串，主键
 * `buyer_info` - 字符串（个人注释 - 可能另一个表的外键更合适）
 * `seller_info` - 字符串（个人注释 - 与上面的注释相同）
 * `credit_card_info` - 取决于卡提供商
 * `is_payment_done` - 布尔值

以下是 `payment_orders` 表包含的内容：
 * `payment_order_id` - 字符串，主键
 * `buyer_account` - 字符串
 * `amount` - 字符串
 * `currency` - 字符串
 * `checkout_id` - 字符串，外键
 * `payment_order_status` - 枚举（`NOT_STARTED`、`EXECUTING`、`SUCCESS`、`FAILED`）
 * `ledger_updated` - 布尔值
 * `wallet_updated` - 布尔值

注意事项：
 * 有许多付款订单，链接到给定的付款事件
 * 我们不需要 `seller_info` 来进行付款流程。仅在付款时需要
 * 当调用相应的服务来记录支付结果时，`ledger_updated` 和 `wallet_updated` 会更新
 * 付款转换由后台作业管理，该作业检查正在进行的付款的更新，并在未在合理的时间范围内处理付款时触发警报

### **复式记账系统**
复式记账机制是任何支付系统的关键。它是一种跟踪资金流动的机制，始终将资金操作应用于两个账户，其中一个账户余额增加（贷方），另一个账户余额减少（借方）：

| 账户 | 借方 | 信用 |
|---------|-------|--------|
| 买家 | $1    |        |
| 卖家 |       | $1     |

所有交易条目的总和始终为零。该机制提供系统内所有资金流动的端到端可追溯性。

## 第 3 步：深入设计
本节重点讨论如何使系统更快、更稳健、更安全。

### **PSP 集成**
如果我们的系统可以直接连接到银行或卡计划，则无需 PSP 即可付款。
这种类型的联系非常罕见且不常见，通常是在可以证明投资合理的大公司中进行的。

如果我们走传统路线，可以通过以下两种方式之一集成 PSP：
 * 通过API，我们的支付系统是否可以收集支付信息
 * 通过托管支付页面，避免处理支付信息法规

以下是托管支付页面工作流程的工作原理：

<div style="margin-left:3rem">
    <img src="./images/hosted-payment-page-workflow.png" alt="hosted-payment-page-workflow" width="500" />
</div>

 * 用户点击浏览器中的“结帐”按钮
 * 客户端使用支付订单信息调用支付服务
 * 支付服务收到支付订单信息后，向PSP发送支付注册请求。
 * PSP 接收支付信息，例如货币、金额、到期时间等，以及用于幂等性目的的 UUID。通常是付款订单的 UUID。
 * PSP 返回一个唯一标识支付注册的令牌。令牌存储在支付服务数据库中。
 * 一旦存储了令牌，就会向用户提供 PSP 托管的支付页面。它使用令牌以及成功/失败的重定向 URL 进行初始化。
 * 用户在PSP页面填写付款详细信息，PSP处理付款并返回付款状态
 * 用户现在被重定向回redirectURL。重定向 url 示例 - `https://your-company.com/?tokenID=JIOUIQ123NSF&payResult=X324FSa`
 * PSP通过webhook异步调用我们的支付服务，通知我们的后端支付结果
 * 支付服务根据收到的webhook记录支付结果

### **和解**
上一节解释了付款的快乐之路。使用后台协调过程来检测和协调不愉快的路径。

每天晚上，PSP 都会发送一个结算文件，我们的系统使用该文件将外部系统的状态与内部系统的状态进行比较。

<div style="margin-left:3rem">

该过程还可用于检测账本和钱包服务之间的内部不一致。

不匹配的情况由财务团队手动处理。不匹配的处理方式如下：
 * 可分类，因此，它是已知的不匹配，可以使用标准程序进行调整
 * 可分类，但无法自动化。由财务团队手动调整
 * 无法分类的。由财务团队人工调查调整

### **处理付款处理延迟**
在某些情况下，付款可能需要几个小时才能完成，但通常只需要几秒钟。

发生这种情况的原因可能是：
 * 付款被标记为高风险，必须有人手动审核
 * 信用卡需要额外的保护，例如3D安全认证，需要持卡人提供额外的详细信息才能完成

这些情况由以下人员处理：
 * 付款完成后等待 PSP 向我们发送 Webhook，或者如果 PSP 不提供 Webhook，则轮询其 API
 * 向用户显示“待处理”状态，并为他们提供一个页面，他们可以在其中签入付款更新。付款完成后我们还可以向他们发送电子邮件

### **内部服务之间的通信**
服务用于相互通信的通信模式有两种类型：同步和异步。

同步通信（即 HTTP）适用于小型系统，但随着规模的增加而受到影响：
 * 性能低——随着调用链中涉及更多服务，请求-响应周期很长
 * 故障隔离不佳 - 如果 PSP 或任何其他服务出现故障，用户将不会收到响应
 * 紧密耦合 - 发送者需要知道接收者
 * 难以扩展 - 由于没有缓冲区，不容易支持流量的突然增加

异步通信可以分为两类。

单个接收者 - 多个接收者订阅同一主题，并且消息仅处理一次：

<div style="margin-left:3rem">
    <img src="./images/single-receiver.png" alt="single-receiver" width="500" />
</div>

多个接收者 - 多个接收者订阅同一主题，但消息会转发给所有接收者：

<div style="margin-left:3rem">
    <img src="./images/multiple-receiver.png" alt="multiple-receiver" width="500" />
</div>

后一种模型非常适合我们的支付系统，因为支付可能会触发由不同服务处理的多种副作用。

简而言之，同步通信更简单，但不允许服务自治。
异步通信以简单性和一致性换取可扩展性和弹性。

### **处理失败的付款**
每个支付系统都需要解决失败的支付问题。以下是我们将用来实现这一目标的一些机制：

 * 重试队列 - 我们将重试的付款会发布到重试队列
 * 死信队列 - 最终失败的支付被推送到死信队列，可以在其中调试和检查失败的支付。

### **一次性交付**
我们需要确保付款只处理一次，以避免向客户重复收费。

如果一个操作同时执行至少一次和最多一次，则该操作仅执行一次。

为了实现至少一次保证，我们将使用重试机制：

<div style="margin-left:3rem">
    <img src="./images/retry-mechanism.png" alt="retry-mechanism" width="500" />
</div>

以下是决定重试间隔的一些常见策略：
 * 立即重试 - 客户端在失败后立即发送另一个请求
 * 固定间隔 - 在重试付款之前等待固定的时间
 * 增量间隔 - 增量增加每次重试之间的重试间隔
 * 指数退避 - 后续重试之间的双倍重试间隔
 * 取消 - 客户端取消请求。当错误已结束或达到重试阈值时会发生这种情况

根据经验，默认采用指数退避重试策略。一个好的做法是服务器使用 `Retry-After` 标头指定重试间隔。

重试的一个问题是服务器可能会处理一次付款两次：
 * 客户点击“付款按钮”两次，因此，他们被收取两次费用
 * PSP 成功处理付款，但下游服务（账本、钱包）未成功处理。重试会导致 PSP 再次处理付款

为了解决双重支付问题，我们需要使用幂等性机制——多次应用的操作只处理一次的特性。

从 API 的角度来看，客户端可以进行多次调用，从而产生相同的结果。
幂等性由请求中的特殊标头（例如 `idempotency-key`）管理，该标头通常是 UUID。

<div style="margin-left:3rem">
    <img src="./images/idempotency-example.png" alt="idempotency-example" width="500" />
</div>

可以使用数据库添加唯一键约束的机制来实现幂等性：
 * 服务器尝试在数据库中插入新行
 * 由于违反唯一键约束，插入失败
 * 服务器检测到该错误并将现有对象返回给客户端

幂等性也应用在 PSP 端，使用前面讨论过的随机数。 PSP 将注意不要使用相同的随机数处理两次付款。

### **一致性**
在支付的整个生命周期中会调用多种有状态服务 - PSP、账本、钱包、支付服务。

任何两个服务之间的通信都可能失败。
我们可以通过实现一次性处理和协调来确保所有服务之间的最终数据一致性。

如果我们使用复制，我们将不得不处理复制延迟，这可能导致用户观察到主数据库和副本数据库之间的数据不一致。

为了缓解这种情况，我们可以从主数据库提供所有读取和写入服务，并仅利用副本来实现冗余和故障转移。
或者，我们可以通过利用 Paxos 或 Raft 等共识算法来确保副本始终同步。
我们还可以使用基于共识的分布式数据库，例如 YugabyteDB 或 CockroachDB。

### **支付安全**
我们可以使用以下一些机制来确保支付安全：
 * 请求/响应窃听 - 我们可以使用 HTTPS 来保护所有通信
 * 数据篡改 - 强制加密和完整性监控
 * 中间人攻击 - 使用 SSL \w 证书固定
 * 数据丢失-跨多个区域复制数据并拍摄数据快照
 * DDoS 攻击 - 实施速率限制和防火墙
 * 卡被盗 - 使用令牌而不是在我们的系统中存储真实的卡信息
 * PCI 合规性 - 处理品牌信用卡的组织的安全标准
 * 欺诈——地址验证、卡验证值（CVV）、用户行为分析等
